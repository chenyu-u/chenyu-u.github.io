Overview

The short version

Researchers wanted to know how people feel inside their apartments during hot summers. Are they too warm, is the air stuffy, are they tired or stressed? Asking once at the end of the day does not work, because people forget. So I built a watch face that buzzes four times a day and asks a handful of questions with big picture buttons. Each answer travels from the watch to a phone, from the phone to the internet, and finally into a spreadsheet the research team can study.

I built this during my summer research position with the Building Energy and Indoor Environment (BEIE) Lab, part of the Hub for Advancing Buildings at the University of Toronto. The study itself belongs to a PhD student in the lab, and it uses a method called ecological momentary assessment, or EMA: short surveys answered in the moment, in the place being studied. The hardware was already decided when I joined, a Fitbit Versa 2 and a dedicated Android phone in each participant kit. My part was the software. I developed the clock face that runs on the watch, the companion app that runs on the phone, the path the data takes after that, and the documentation that lets someone else rebuild the whole thing.

System architecture

The system is built in four layers, and each layer does exactly one job before handing the data to the next. That structure is deliberate. When something goes wrong, it means the fault can be traced to a single place.

LayerRuns onResponsibility
Watch appFitbit OS, SDK 4.2Draws the clock and the SURVEY button, keeps the schedule, shows one question at a time, and sends the finished answers to the phone.
CompanionFitbit mobile app on AndroidTurns the answers into one flat record, stamps it with the participant ID and the local time, keeps a local CSV backup, uploads it, and retries if the upload fails.
Cloud storeJSONBinHolds every session from every participant as one JSON array.
RetrievalNode.js on a laptopDownloads the array and writes a CSV with one row per session.

Engineering design process

  1. Define the problem

    Step 1 · Problem definition
    In plain words

    The lab needed a way to ask people how they feel at home, several times a day, without a researcher being there.

    The study looks at how residents of multi-unit residential buildings experience summer heat. To do that well, the research team needed self-reported comfort and wellbeing data collected several times a day over an entire summer, from participants who were simply going about their lives. And the answers had to arrive as clean, analysis-ready data, with nobody transcribing anything by hand.

  2. Set requirements and constraints

    Step 2 · Requirements
    In plain words

    Before writing any code, I wrote down what the survey had to do and the limits I had to work inside.

    The survey had to prompt participants at 9:00, 12:00, 15:00 and 18:00, and it also had to let them start a survey themselves whenever they felt uncomfortable. It had to fit on a 300 by 300 pixel screen and be answered in a few taps, with no typing, using large icons and colour cues rather than small text. On privacy, it could record survey answers only, with no heart rate, steps or any other Fitbit health data, and every record had to be labelled with a study ID rather than an account.

    There were practical constraints too. An answer could not be lost just because the phone had no internet at that moment. The storage service had to fit inside a free tier, and the arithmetic worked out: twenty kits, four surveys a day and two requests per survey comes to about 160 requests a day, comfortably inside a limit of roughly 10,000 a month. Finally, the platform was fixed. A Versa 2 means Fitbit SDK 4.2, which means an older JavaScript engine on the watch and Node 14 for the build tools.

  3. Make the key design decisions

    Step 3 · Concept selection
    In plain words

    I made the survey the watch face itself, so it is already on screen the moment someone looks at their wrist.

    The first decision was whether to build an app or a clock face. A Fitbit app has to be opened from a menu, while a clock face is always showing. I registered the project as a clock face, so the participant raises their wrist and the survey is simply there, with nothing to find. Between surveys, the watch still works as a watch.

    The second decision was how to build the screens. Rather than drawing a separate screen for each question, I built one layout with a two-button row and a three-button row, and I described every question as an entry in an array. The code fills in the text, the icons and the colours from that array. Adding or rewording a question means editing one object, which mattered because the question set changed while I was developing it.

    The third decision was where the data should live. The companion can make ordinary HTTPS requests, so a simple hosted JSON store was enough. That removed the need to run, secure and pay for a server for a tool built by a student.

  4. Design the survey logic and the data record

    Step 4 · Detailed design
    In plain words

    I drew the path a survey takes as a flowchart first, so every possible ending was decided before I wrote code.

    The first question asks whether the participant is at home. The study is about conditions inside the apartment, so if the answer is no, the survey ends right there and a short record is saved. That keeps the burden on the participant low, and it still tells the researchers that the prompt was seen.

    Every session is stored as one flat record with the same fourteen fields every time. A question that was not shown is stored as null, which becomes an empty cell in the CSV. Because the shape never changes, the analysis scripts never have to guess which columns exist.

    Timestamps needed some care as well. JavaScript's built-in timestamp is in UTC, but the survey schedule runs in the participant's local time. I wrote a small helper that records local time with its offset, for example 2025-09-01T09:04:22-04:00, so a 9:00 survey reads as 9:00 in the data.

  5. Build within the platform limits

    Step 5 · Implementation
    In plain words

    The watch is a tiny, older computer. Some things that work on a laptop do not work on it, and I had to find out which.

    The first surprise was that the SDK 4.2 runtime on the watch does not support arrow functions, so every handler in the watch code is a named function. The companion runs on the phone in a newer engine and has no such limit. The second was that click events were unreliable on the device, while a mousedown event on a transparent rectangle placed over each button registered every single time.

    The icon set caused a different kind of problem. The artwork was dark on a transparent background, which simply disappears on a black watch screen. I placed a coloured tile behind every icon, and that colour then became part of the interface: green for comfortable, red and blue for the two opposite directions, and yellow for neutral. Along the way I also found that an image element declared without a starting file could fail to initialise, and the code could not set one later, so every image in the layout now begins with a valid placeholder.

  6. Test, find faults, fix them

    Step 6 · Verification
    In plain words

    I used the watch the way a real participant would, including ignoring it, and fixed the problems that only show up that way.

    The most serious fault appeared when I ignored a survey. The next timer was only set when a survey finished, and an unanswered survey never finishes, so every survey after that one stopped firing. The fix was to queue the next slot at the start of every survey, before the first question is even shown. A related fault was that a manual survey which was ignored left its flag set, so the next scheduled session was labelled as manual. Now the timer callback clears that flag before it starts anything.

    The sleep question had its own problem. It was tied to the 9:00 slot, so anyone who was out in the morning never saw it. I moved it so that it is inserted after the first "yes, I am home" of the day, and the date is recorded only when the question is actually displayed. On the phone side, an upload was originally attempted once, which meant a session was lost if the phone happened to be offline. The companion now writes to a local CSV first, holds the session in a buffer, and retries on every reconnect. And one fault had nothing to do with code at all: the university network blocks the developer bridge between the laptop and the phone, so installing to the watch on campus was impossible. Sideloading over a phone hotspot on the 2.4 GHz band, which is the only band the Versa 2 supports, solved it.

  7. Verify on hardware and hand over

    Step 7 · Handover
    In plain words

    I proved the app worked on a real watch, then wrote instructions so the person running the study could load the rest without me.

    My focus was the development of the clock face and the companion, so I loaded and verified the app on a single test watch. That check runs end to end: complete a survey on the watch, see the green Saved screen, then confirm that the record appears in the cloud store under the right participant ID. The PhD student who owns the study sideloaded the remaining watches and deployed the kits to participants.

    To make that handover work, I wrote a 24-section development guide covering the architecture, the build environment, the sideloading procedure, the data schema, the verification check and every known failure with its fix. Research software is often lost when the student who wrote it leaves. The guide is there so that this one is not.

  8. Review the result

    Step 8 · Evaluation
    In plain words

    It does the job. I also know where its weak spots are, and I wrote them down.

    The app now supports a multi-summer study with more than 20 participants and delivers a CSV the team can analyse directly. It also has limitations that I documented for the lab. Timers live in memory, so if the watch restarts, the schedule only resumes when the clock face reloads, because Fitbit OS gives a clock face no persistent alarm. The watch does not buffer, so if the phone is out of Bluetooth range at the moment a survey ends, that session is lost, since buffering happens on the phone only.

    The last one is more subtle. Each upload downloads the whole array, appends one record and writes it back, and that sequence is not atomic. Two phones uploading in the same second could overwrite each other. At 160 uploads a day the risk is small, and the local CSV backup covers it, but the correct fix is an append-only endpoint or a separate store for each participant.

Watch app

A question is data, not code

Every question is one object like this one. The screen code never mentions temperature or humidity. It only knows how to draw whatever object it is given.

The value is what gets stored, the label is what the participant sees, and the color is the tile drawn behind the icon.

Watch app

Schedule the next survey first

This ordering is the fix for the most serious fault found in testing. Because scheduleSurvey() runs before the first question appears, the 12:00 survey is already queued even if the 9:00 one is never answered.

The sleep question is filtered out at the start and added back later, but only if the participant says they are home. The three short vibrations are spaced 600 ms apart so the prompt is hard to miss.

messaging.peerSocket.addEventListener("message", (evt) => {
  const message = evt.data;
  if (message && message.type === "survey_response") {
    const session = buildSession(message.payload,
      message.triggeredManually || false,
      message.includesSleep     || false);
    appendToLocalCSV(session);      // 1. local backup first
    stagedResponses.push(session);  // 2. hold in retry buffer
    pushSession(session);           // 3. try the upload
  }
});

// When the watch reconnects, retry anything still buffered.
messaging.peerSocket.addEventListener("open", () => {
  stagedResponses.forEach(session => pushSession(session));
});
Phone companion

Never lose an answer

When answers arrive from the watch, three things happen in a fixed order. The session is backed up locally, placed in a retry buffer, and then uploaded. It leaves the buffer only after the server confirms it.

The second handler runs every time the watch reconnects and retries anything that is still waiting.

What this project taught me

Test the unhappy path

The worst fault only appeared when a survey was ignored, which is exactly what real participants do. Testing only the expected behaviour would have missed it entirely.

Design the data first

Fixing the shape of the record early meant the watch, the phone and the download script could be written and changed independently of each other.

Documentation is part of the deliverable

In a research lab, the next person to touch the code is another student. If they cannot rebuild it, it may as well not exist.

Be honest about limits

Every system has weak points. Writing them down, along with the conditions that trigger them, is far more useful than pretending they are not there.
