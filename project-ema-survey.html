A custom Fitbit OS clock face and phone companion app that survey study participants four times a day and deliver their answers to the research team as a comma-separated values file ready for analysis. I developed it in JavaScript, SVG and CSS for a multi-summer heat-exposure study in residential buildings.

Overview

The short version

The study needed to know how residents feel inside their apartments during hot summers. Are they too warm, does the air feel stuffy, are they tired or stressed? End-of-day surveys rely on memory, so this app asks in the moment instead. The watch face buzzes four times a day and asks a few questions with large picture buttons. Each answer moves from the watch to a paired Android phone, from the phone to a cloud store, and into a file the research team can analyze.

I developed this app during my summer research internship with the Building Energy and Indoor Environment Lab, part of the Hub for Advancing Buildings at the University of Toronto. The study is led by a PhD candidate in the lab and uses ecological momentary assessment, a method where participants answer short surveys in the moment and in the environment being studied. Each participant kit pairs a Fitbit Versa 2 with a dedicated Android phone. I was responsible for the software: the watch clock face, the phone companion, the data pipeline to the cloud, and the technical documentation the lab uses to rebuild and maintain the system. The page follows the project in the order I worked through it, from the research need to the handover.

Engineering design process

  1. Define the problem

    Step 1 · Problem definition
    In short

    The lab needed several self-reported surveys a day from each participant, with no researcher present.

    The study looks at how people in multi-unit residential buildings experience summer heat. That required comfort and wellbeing data collected several times a day over a whole season, from participants going about their normal routines. The data also had to arrive clean and ready to analyze, with no manual transcription.

  2. Set requirements and constraints

    Step 2 · Requirements
    In short

    Before writing any code, I set out what the survey had to do and the limits it had to work within.

    • Scheduling: prompts at 9:00, 12:00, 15:00 and 18:00, plus a survey participants can start any time they feel uncomfortably hot or cold.
    • Usability: each survey fits a 300 by 300 pixel screen and takes a few taps with no typing, using large icons and colour cues.
    • Privacy: survey answers only, with no heart rate, activity or other health data, and every record tied to a study ID instead of a personal account.
    • Reliability: no answer is lost if the phone is briefly offline.
    • Cost: storage fits a free tier. Twenty kits, four surveys a day and two requests per survey come to about 160 requests a day, well under the limit of roughly 10,000 a month.
    • Platform: the Versa 2 requires Fitbit SDK 4.2, which means an older JavaScript runtime on the watch and Node 14 for the build tools.

  3. Make the key design decisions

    Step 3 · Concept selection
    In short

    I made the survey the watch face itself, so it is on screen the moment a participant looks at their wrist.

    • Clock face, not an app. A Fitbit app has to be opened from a menu, but a clock face is always displayed. Building the survey as a clock face put it in front of participants as soon as they raised their wrist, and the device still works as a watch between surveys.
    • Data-driven interface. I built one template with a two-option row and a three-option row that renders every question from a configuration list. The display code fills in the text, icons and colours from the list, so adding or rewording a question is a one-entry edit. That paid off when the questions changed during development.
    • Hosted storage. The companion sends standard web requests, so a hosted JSON store could handle the data, with no server to set up, secure or pay for.

    From those decisions I split the system into four layers. Each layer has one job and passes its data to the next in a fixed format, so any fault can be traced to a single layer.

    LayerPlatformResponsibility
    Watch applicationFitbit OS, SDK 4.2Displays the clock face and the SURVEY button, keeps the schedule, shows one question at a time, and sends completed answers to the phone.
    CompanionFitbit mobile app on AndroidBuilds a flat record for each survey, stamps it with the participant ID and local time, saves a local comma-separated values backup, uploads it, and retries if the upload fails.
    Cloud storeJSONBinStores every survey from every participant in a single JSON array.
    RetrievalNode.js on a laptopDownloads the array and converts it to a comma-separated values file with one row per survey.

  4. Design the survey logic and the data record

    Step 4 · Detailed design
    In short

    I mapped every survey path in a flowchart before writing any code.

    The first question asks whether the participant is home. The study is about conditions inside the apartment, so a "no" ends the survey right away and saves a short record. That keeps the burden on participants low while still confirming they got the prompt.

    I designed every survey to save as one flat record with the same fourteen fields. A question that was not asked is stored as null and shows up as an empty cell, so the analysis scripts never have to guess which columns are present.

    Timestamps are recorded in the participant's local time with the UTC offset, for example 2025-09-01T09:04:22-04:00. I wrote a helper for this because JavaScript records time in UTC by default, and without it a 9:00 survey would not read as 9:00.

  5. Build within the platform limits

    Step 5 · Implementation
    In short

    I built the watch app within the limits of an older, constrained device.

    The SDK 4.2 runtime on the watch does not support arrow functions, so I wrote the watch code with named functions throughout. The phone companion runs on a newer engine with no such limit. For touch input, I replaced click events, which were unreliable on the device, with a mousedown event on a transparent rectangle over each button.

    I placed each icon on a coloured tile so the dark artwork stays visible on the black screen. The colours also carry meaning: green for comfortable, red and blue for the two opposite directions, and yellow for neutral. Every image in the layout starts with a valid placeholder, which works around a platform bug where an image without a starting source can refuse to load later.

  6. Test, find faults, fix them

    Step 6 · Verification
    In short

    I tested the app the way real participants use it, including surveys they ignore.

    • Ignored surveys. The next survey was originally scheduled only after the current one finished, so one ignored survey stopped every later one. I changed it to schedule the next survey at the start of each survey. A related fix clears the manual-survey flag, so an ignored manual survey no longer mislabels the next scheduled one.
    • Sleep question. It was tied to the 9:00 survey, which missed anyone not home in the morning. I moved it so it is asked the first time each day a participant says they are home, and its date is recorded only when it is actually shown.
    • Offline uploads. The first version tried each upload once. I changed the companion to save a local comma-separated values backup, hold each survey in a buffer and retry on every reconnection, so a brief offline moment no longer loses data.
    • Deployment. The university network blocked the developer connection to the watch, so I installed it over a phone hotspot on the 2.4 GHz band, the only band the Versa 2 supports.

  7. Verify on hardware and hand over

    Step 7 · Handover
    In short

    I verified the app end to end on hardware and documented it for the lab to deploy.

    I installed and verified the app end to end on a test watch: complete a survey, check the confirmation screen, and confirm the record reaches the cloud store under the right participant ID. The PhD candidate leading the study then installed it on the remaining watches and deployed the kits.

    For the handover I wrote a 24-section development guide covering the architecture, build setup, installation, data format, testing procedure, and every known failure with its fix. Research software is often lost when the student who wrote it graduates, and the guide keeps this system maintainable.

  8. Review the result

    Step 8 · Evaluation
    In short

    The app went into use in the study, and I documented its limitations for the lab.

    The app supports a multi-summer study with more than 20 participants and delivers a file the research team can analyze directly. I documented three limitations for the lab:

    • Timers live in memory, because Fitbit OS gives clock faces no persistent alarm. After a restart, the schedule resumes once the clock face reloads.
    • Only the phone buffers answers. A survey completed while the phone is out of Bluetooth range is lost.
    • Each upload reads the full data list, adds a record and writes it back, which is not atomic, so two uploads in the same second could overwrite each other. At 160 uploads a day that is unlikely, and the local backups allow recovery, but an append-only endpoint or a separate store for each participant would remove the risk.

Watch app

Schedule the next survey first

This order is the fix for the most serious bug I found in testing. Because scheduleSurvey() runs before the first question appears, the 12:00 survey is scheduled even if the 9:00 survey is never answered.

The sleep question is removed at the start and added back later, but only if the participant says they are home. The three vibrations are 600 ms apart so the prompt is hard to miss.

messaging.peerSocket.addEventListener("message", (evt) => {
  const message = evt.data;
  if (message && message.type === "survey_response") {
    const session = buildSession(message.payload,
      message.triggeredManually || false,
      message.includesSleep     || false);
    appendToLocalCSV(session);      // 1. local backup first
    stagedResponses.push(session);  // 2. hold in retry buffer
    pushSession(session);           // 3. try the upload
  }
});

// When the watch reconnects, retry anything still buffered.
messaging.peerSocket.addEventListener("open", () => {
  stagedResponses.forEach(session => pushSession(session));
});
Phone companion

Never lose an answer

When answers arrive from the watch, three things happen in a fixed order: save a local backup, add the survey to the retry buffer, then upload it. A survey only leaves the buffer once the server confirms it was received.

The second handler runs every time the watch reconnects and retries any survey that is still waiting.

What this project taught me

Test the unhappy path

The worst bug only showed up when a survey was ignored, which is exactly what real participants do. Testing only the normal case would have missed it.

Design the data first

Locking in the record format early let me build and revise the watch app, the phone app and the download script independently.

Documentation is part of the deliverable

In a research lab, the next person to maintain the code is usually another student. Software nobody else can rebuild was not really finished.

Be explicit about limits

Every system has ways it can fail. Writing them down, along with what causes them, was more useful to the lab than leaving them out.
